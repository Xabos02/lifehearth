# Протокол LifeHearth

Единый стандарт дизайна, кода и подачи для этого приложения. Не идеология —
опись решений, которые уже приняты и подтверждены кодом, плюс правило, как
принимать новые в том же духе. Каждое число здесь взято из `src/index.css`,
`design/`, компонентов или тестов — придуманных токенов и шрифтов в этом
документе нет.

**Как пользоваться.** Перед правкой экрана, компонента или текста в
интерфейсе — открыть раздел, который касается задачи (цвет, типографика,
иконки, движение, тон, структура), сверить решение с ним. Если в протоколе
пробел — решение всё равно должно укладываться в дух остальных разделов
(премиальный минимализм, точность вместо приблизительности, честность перед
пользователем), а затем сюда дописывается.

## 0. Референсы и что именно взято

Ориентир — не абстрактный «топ-5 приложений мира», а три конкретных, и у
каждого взято ровно то, что подтверждено решением в коде:

- **Apple (HIG + системные приложения).** Минимальная зона касания 44×44 —
  жёсткое правило, проверяется тестом (`e2e/touch.spec.ts`). Чекбоксы —
  скруглённый квадрат, как в списках iOS. Жесты и структура папок в заметках
  — по образцу Apple Notes (`e2e/notes-folder-order.spec.ts`,
  `e2e/notes-select.spec.ts`, `e2e/notes.spec.ts`): редактор пишет на чистом
  листе без рамки фокуса, вложенные папки создаются на текущем уровне. Кастомный
  набор иконок нарисован по правилам SF Symbols: крупная форма, минимум деталей,
  силуэт узнаётся на 14px (`src/components/ui/glyphs.tsx`). Стрелка «назад» с
  подписью родителя («‹ Заметки»), а не голая стрелка — тоже паттерн iOS
  (`src/components/layout/Screen.tsx`).
- **Linear и Vercel.** Источник выбора шрифта — Inter как экранный гротеск с
  полноценной кириллицей вместо system-ui, который на Android/десктопе даёт
  Roboto и оставляет приложение без своего лица (`src/index.css`).
- **Общий принцип премиальных интерфейсов**, вынесенный из формулировок в
  самом коде: *точность важнее приблизительности* (контраст меряется по
  пикселям в браузере, а не прикидкой по таблице токенов — `e2e/contrast.spec.ts`),
  *спокойствие важнее эффектности* (появление сообщения — «короткий подъём без
  пружины: спокойный ритм ленты важнее эффектности», `src/index.css`), *честность
  перед пользователем важнее конверсии* (раздел «Женские дни» не должен
  притворяться скрытым для семьи полумерами — ни плашкой, ни серым слотом,
  `docs/cycle-tracking-research.md:539`).

Дизайн-решения владельца по конкретным экранам фиксируются на канве
(`design/*.dc.html`, `design/canvas.json`) — сравнение вариантов до вёрстки,
а не правка стиля «по вдохновению» прямо в компоненте (правило зафиксировано
в `CLAUDE.md` проекта, раздел «Дизайн — только через `/design`»).

## 1. Цвет

Источник истины: `:root` и `:root.light` в `src/index.css`. Палитра — OKLCH,
глубокий тёплый-тёмный с фиолетово-индиговым подтоном; нейтрали тонированы
к одному hue, хрома снижена у крайних L.

### 1.1. Текст и заливка — разные токены, не переиспользовать

```
--app-<имя>        цвет ТЕКСТА и иконок на поверхности
--app-<имя>-fill   ЗАЛИВКА (кнопка, чип, плашка), подобранная под свой глиф
--app-on-light     тёмный глиф для светлых заливок
```

Причина — измеренный факт, а не перестраховка: токены изначально подбирались
как текст на тёмной поверхности (контраст 6–10:1) и в этой роли хороши, но
белый глиф на заливке `accent` даёт 2.62, на «успехе» 1.75, на «предупреждении»
1.71 при норме WCAG AA 4.5 — измерено по пикселям, `scratchpad/contrast-dom.mjs`.
**Правило: заливка кнопки/чипа всегда берётся из `*-fill`-токена, глиф на ней —
не автоматически белый, а по типу цвета:**

- холодные насыщенные (`accent`, `accent-2`, `danger`, `focus`) — заливка
  темнеет до L≈0.58, глиф остаётся белым;
- светлые по смыслу (`success`, `warning`, `frost`) — заливка остаётся яркой,
  глиф тёмный (`--app-on-light`); затемнять зелёный до синевы ради контраста
  значило бы менять смысл цвета.

### 1.2. Контраст — измеряется, не постулируется

Минимум WCAG AA (4.5:1) проверяется в реальном браузере через canvas
(`e2e/contrast.spec.ts`), а не по таблице токенов: один цвет лежит на трёх
разных поверхностях (`bg`, `surface`, `surface-2`) и на собственной подложке
(`bg-accent/15` у чипов), и контраст на каждой свой. Значения L подбираются
бинарным поиском по худшей из поверхностей, ровно до 4.5 — не глубже, чтобы
цвет не терял себя.

Пример решения по фактическому замеру: счётчик задач у заголовка проекта
цветной только в тёмной теме — в светлой голая цветная цифра проваливает AA
у всех 27 цветов палитры (лучший результат 4.45, худший 1.08 у белого), и
`:root.light` возвращает серый (`src/index.css`, `.project-count`).

**Правило: новый цветной элемент на новом фоне — не «выглядит нормально», а
прогоняется через тот же тип замера** (или добавляется в `contrast.spec.ts`),
особенно если элемент есть в обеих темах.

### 1.3. Тёмная и светлая темы — не зеркала друг друга

Светлая тема не получается инверсией тёмной: акцентный текст в ней подбирается
по худшей из трёх поверхностей отдельно (см. комментарий у `--app-accent` в
`:root.light`), а заливки почти не двигаются — там белый глиф и так проходит.
Обе темы держат `color-scheme` (`dark` / `light`) для нативных контролов.

### 1.4. Локальные акценты разделов

Раздел может переопределять акцент **только внутри своей обёртки**, не трогая
нейтрали и не влияя на остальные экраны:

- `--focus-accent` / `--focus-accent-2` — тёплый красно-оранжевый, «Фокус», в
  духе Focus To-Do;
- `--cc-accent` / `--cc-accent-2` — акцент раздела ИИ.

Правило явно проговорено в коде: «нейтрали приложения не перетонируем — это
дало бы регресс на всех 20+ экранах ради одного раздела» (`src/index.css`).
Новый локальный акцент — только по той же схеме: 2–4 цветовых токена и тень,
без изменения `--app-bg/surface/border/text`.

### 1.5. Смысловые цвета — фиксированы

`danger` (ошибка/удаление), `success`, `warning`, `frost` — общие для всего
приложения, переопределяются только между темами, не между разделами. Менять
смысл цвета (например, затемнять success до синевы ради формального контраста)
запрещено явно комментарием в коде.

## 2. Типографика

### 2.1. Шрифт

**Inter**, самостоятельно захостен (`public/fonts`, не CDN) — приложение
обязано работать офлайн. Два подмножества вместо семи — кириллица и латиница,
раздельные `unicode-range`, суммарно 65 КБ, `font-display: swap`.
`-apple-system` остаётся в стеке ПОСЛЕ Inter как запасной, не как основной.
**Новый шрифт (в том числе на отдельный раздел) не добавляется без такого же
самостоятельного хостинга и разбиения на подмножества.**

### 2.2. Корень 17px и шкала кеглей

Корень приложения — **17px**, а не 16px по умолчанию браузера: при 16px и
Tailwind-шаге в rem базовая единица сетки выходила дробной (4.25px), из-за
чего ни один отступ и ни один радиус в интерфейсе не были целыми числами
(6.38, 8.5, 10.63...) — отсюда дрожание hairline-линий на DPR 3. Кегли
намеренно остаются в px, шаг сетки (`--spacing`) — тоже в px, не в rem.

Восемь ступеней вместо произвольных значений (было 47 случайных плюс 5
`clamp()` — по одной на каждый случай, где «не хватило» стандартной):

| Токен | Размер | Интерлиньяж | Трекинг |
|---|---|---|---|
| `text-2xs` | 11px | 1.35 | — |
| `text-xs` | — | 1.35 | 0.005em |
| `text-sm` | 15px | 1.45 | — |
| `text-base` | 17px | 1.45 | — |
| `text-lg` | 20px | 1.25 | -0.01em |
| `text-2xl` | 26px | 1.15 | -0.015em |
| `text-3xl` | 32px | 1.1 | -0.02em |
| `text-5xl` | 48px | 1 | -0.03em |

**Правило: размер, интерлиньяж и трекинг задаются вместе, одной ступенью, а не
по отдельности.** Произвольный `text-[15px]` без пары «крадёт» интерлиньяж
1.5 из preflight — строка выходит разреженнее соседней. Крупный кегль без
отрицательного трекинга выглядит разъехавшимся, мелкий без положительного —
слипшимся (было 7 мест из 20 без компенсации: «21°» в погоде и счётчики
фокуса шли с нулевым трекингом).

Три пояса интерлиньяжа по смыслу текста: **1.1–1.15** — дисплейные числа и
крупные заголовки; **1.25–1.35** — подписи и однострочники; **1.45** — проза.

**Правило: новая ступень кегля не заводится по потребности одного экрана.**
Если восьми ступеней не хватает — это повод пересмотреть композицию экрана,
а не добавить девятую.

## 3. Сетка, отступы, радиусы, тени

`--spacing: 4px` — базовый шаг Tailwind, в пикселях (см. 2.2, почему не rem).
Все отступы кратны 4px.

Радиусы — шесть ступеней, не произвольные значения:

| Токен | Значение |
|---|---|
| `radius-sm` | 4px |
| `radius-md` | 6px |
| `radius-lg` | 8px |
| `radius-xl` | 12px |
| `radius-2xl` | 16px |
| `radius-3xl` | 24px |

Тени — именованные по назначению, не по размеру: `--shadow-card` (карточка
над подложкой), `--shadow-pop` (всплывающее — шит, тост), `--shadow-accent`
(акцентная кнопка, цвет тянется из `--app-accent`), `--shadow-tile` (плитка
знака — мягче акцентной, только отделяет от карточки), `--shadow-focus`
(раздел «Фокус», свой оттенок). Новая тень — не `box-shadow` россыпью в
компоненте, а именованный токен с комментарием, что он отделяет от чего.

Нижний отступ страницы — 16px фиксированно (`Screen.tsx`): без него нижняя
карточка визуально «упирается» в край ленты, а тень карточки (уходит на 24px
вниз) обрезается скролл-контейнером без запаса.

## 4. Иконки

Источник: `src/components/ui/icons.ts`, `src/components/ui/glyphs.tsx`.

### 4.1. Толщина штриха — в пикселях готового рисунка, не в единицах сетки

`absoluteStrokeWidth` включён на провайдере lucide в `App.tsx`, поэтому три
константы ниже — пиксели финального штриха при любом размере иконки, а не
доли сетки 24×24 (иначе один и тот же вес даёт втрое разную толщину на 14px
и 40px):

- `STROKE = 1.7` — обычный вес;
- `STROKE_STRONG = 2` — акцент: активная вкладка, кнопка тулбара, дисплейная
  иконка в заглушке;
- `STROKE_HEAVY = 2.4` — глиф поверх плотной заливки (галочка в квадрате,
  «плюс» на градиенте — тонкий штрих там съедается ореолом сглаживания).

Пять ступеней размера с ролями (`ICON.*` в `icons.ts`): `inline` (значок в
строке текста), `action` (действие в строке списка), `base` (основная —
шиты, ряды, кнопки), `header` (шапка, шевроны), `accent` (плавающая кнопка,
плеер, звонок), плюс дисплейная группа для заглушек и обложек.

**Правило: новый размер иконки не подбирается на глаз.** Соседние произвольные
значения (17 и 18) визуально неотличимы и читаются как небрежность — берётся
существующая ступень.

### 4.2. Собственный набор глифов — правила рисунка

Кастомные глифы (таб-бар, плитки разделов, панель форматирования, частые
действия) нарисованы по правилам SF Symbols, а не заимствованы у lucide
как есть — у lucide «инженерный» рисунок с разной оптической плотностью
между соседними иконками, что на экране телефона читается как шум:

- сетка 24×24, живая область — квадрат 20×20 (2px поля);
- толщина штриха не задаётся в самом глифе — только геометрия, вес приходит
  извне (§4.1);
- концы и стыки скруглены;
- радиус скруглений: 2 у мелких форм, 3–4 у крупных — один радиус на весь
  набор выглядит либо колюче, либо мыльно;
- окружности предпочитаются многоугольникам, симметрия — асимметрии;
- ничего мельче 2 единиц сетки — на 14px деталь схлопывается в пятно.

**Граница осознанная, не долг:** перерисовано то, что человек видит
постоянно; редкие иконки в глубине настроек остаются на lucide — та же
сетка 24, те же скруглённые концы, тот же вес, различие в подробности рисунка
там не мешает. Смесь двух наборов заметна только при прямом сравнении двух
экранов рядом.

## 5. Компоненты и зоны касания

### 5.1. 44×44 — не рекомендация, а проверяемый минимум

Минимум Apple HIG для интерактивных элементов — жёсткое правило с тестом
(`e2e/touch.spec.ts`, сканирует `button, a[href], [role="button"]` на всех
основных экранах). Там, где визуально контрол должен остаться мелким
(чекбокс списка, иконка-кнопка) — область касания расширяется невидимым
псевдоэлементом `::after` (`HIT_SLOP_44`, `src/components/ui/hitSlop.ts`),
а не увеличением самого элемента: плотность списков сохраняется, хит-зона
растёт отдельно.

Два условия, чтобы приём не сломался: у элемента не должно быть
`overflow: hidden` (обрежет и хит-зону тоже), и до соседнего интерактивного
элемента нужно ≥11px зазора — иначе зоны перекрываются и промах засчитывается
не тому элементу.

### 5.2. Каркас страницы (`Screen.tsx`)

Липкая шапка с safe-area + контент. Заголовок либо `title`, либо, для
экранов без собственного заголовка (редактор заметки), — `backLabel` с именем
родителя рядом со стрелкой назад, набранное обычным кеглем: паттерн iOS
«‹ Все заметки», объясняющий, куда ведёт стрелка, не споря визуально с
заголовком самого экрана.

### 5.3. Кнопки (`Button.tsx`)

Четыре варианта, без добавления новых без необходимости: `primary` (заливка
акцентом), `secondary` (заливка `surface-2`), `ghost` (прозрачный, акцентный
текст), `danger` (заливка `danger/15`, текст `danger`). Нажатие — `scale-[0.98]`
на 150ms, не мгновенный скачок и не пружина (см. §6 про ритм движения).

### 5.4. Пустые состояния

`EmptyState`: иконка в карточке-плашке, заголовок, необязательная подсказка.
Отступы сверху и снизу асимметричны намеренно — блок стоит выше
геометрического центра, где глаз ищет его первым.

## 6. Движение и анимация

Принцип, сформулированный прямо в коде: **спокойный ритм важнее эффектности.**
Появление нового сообщения в чате — короткий подъём (`translateY(6px)` →
`none`) за 180ms на `cubic-bezier(0.165, 0.84, 0.44, 1)`, без пружины.
Каретка печатающегося ответа мигает шагами (`steps(2, jump-none)`), не
плавным fade — терминальная каретка «щёлкает», а не «дышит»: это фирменный
знак ленты ИИ, не общий тик анимации.

### 6.1. `prefers-reduced-motion` — глобальное правило, не точечное

Системный тумблер «уменьшить движение» гасит **все** анимации и transition
через один селектор `*, *::before, *::after` (`src/index.css`), включая
инлайновые `transition` в атрибуте `style` (кольцо таймера, шит, строка
задачи) — до атрибута `style` модификатор `motion-reduce:` в Tailwind не
дотягивается в принципе. До этого блока учтённых мест было два из шести с
лишним десятков.

**Длительность гасится до `0.01ms`, не до `0`:** нулевая длительность в части
браузеров не порождает событие `transitionend`, и код, который его ждёт,
зависает навсегда. Любая новая анимация автоматически подчиняется этому
блоку, если использует `animation`/`transition` — отдельно её вносить не
нужно, но если анимация не CSS (JS-таймер, requestAnimationFrame), она не
попадает под общее правило и должна проверять `matchMedia` сама.

### 6.2. Печать — отдельный, не анимационный, но тот же принцип «глобально, не точечно»

`@media print` — общее правило на `header`, `nav`, `.print-hide`, а не класс
на конкретном экране отчёта: `window.print()` печатает весь текущий DOM.
Чёрным по белому независимо от темы — лист принтера белый всегда, даже если
интерфейс в тёмной теме.

## 7. Тон и подача текста

### 7.1. «Что нового» — обязательная часть коммита, не факультатив

Каждое изменение, которое человек видит или делает иначе — новая запись в
`src/lib/changelog.ts` **в том же коммите**, что и сама правка (правило уже
зафиксировано в `CLAUDE.md` проекта). Приложение обновляется тихо (service
worker сам подменяет версию), и этот список — единственный способ, которым
пользователь (в том числе не владелец — в семейном разделе есть другие люди)
узнаёт, что изменилось.

Как писать пункт:

- отвечать на вопрос «что мне теперь доступно», а не «что вы починили»;
- пользовательским языком, без имён компонентов и файлов: «разделы на
  „Главной" собраны в один список», а не «MenuCard переведён на общий
  контейнер»;
- изменения без следа в интерфейсе (рефакторинг, тесты, сборка) в список
  не идут — иначе он превращается в шум, который перестают читать.

### 7.2. Честность важнее заглаженности

Если функция скрывает данные от части пользователей (семейный раздел,
цикл), в интерфейсе не должно быть следов существования скрытого — ни
плашки «скрыто», ни серого слота, ни пустого места с пометкой: сам факт
скрытия — тоже информация, которую нельзя утечь (`docs/cycle-tracking-research.md:539`,
со ссылкой на паттерн Apple HealthKit: «отказ неотличим от отсутствия»).
То же для формулировок: если код фактически кладёт данные раздела в общий
бэкап, текст в интерфейсе не имеет права утверждать обратное — расхождение
между обещанием в UI и поведением кода фиксируется как дефект, а не как
разница между «пока» и «потом».

### 7.3. Комментарии в коде — часть протокола, не документация для галочки

Комментарии в этой кодовой базе объясняют **решение и его альтернативу**, а
не то, что делает код (это видно по самому коду): «было X, стало Y, потому
что при X ломалось Z» — см. любой из токенов в `src/index.css`. Новый
неочевидный визуальный или цветовой выбор оформляется тем же способом: не
«акцент 0.58», а почему 0.58, а не 0.5 и не 0.65.

## 8. Структура и архитектура (что уже есть)

- **React 19 + TypeScript + Vite, Tailwind CSS 4** (CSS-first, токены в
  `src/index.css`, а не в `tailwind.config`).
- **Dexie.js (IndexedDB)** — локальное хранилище, `useLiveQuery` как слой
  состояния. Все записи наследуют `BaseEntity` (`id`, `createdAt`,
  `updatedAt`, `deletedAt` — мягкое удаление) и идут только через
  `src/db/repo.ts` (`create`/`update`/`remove`) — прямая запись в таблицу
  в обход repo нарушает sync-штампы.
- **PWA офлайн-first** (vite-plugin-pwa, precache всего билда, `autoUpdate`)
  — это ограничивает выбор шрифтов, шрифтовых CDN и любых внешних
  синхронных зависимостей рендера: должно работать без сети.
- **Организация кода по фиче** (`src/features/<раздел>/`), общие
  UI-примитивы — в `src/components/ui/`, каркас — в `src/components/layout/`.
- **E2E-шифрование там, где это уже принцип** (синк, семейный чат, звонки) —
  новый канал передачи личных данных на сервер по умолчанию проектируется
  так же, а не как открытый текст с оговоркой «пока».

## 9. Процесс: дизайн только через канву

Требование владельца (зафиксировано в `CLAUDE.md` проекта, 10.09.2026):
любое визуальное решение — экран, иконка, оформление — проходит через
артборды в `design/*.dc.html` (сравнение вариантов рядом), а не правится
точечно прямо в компоненте «по вдохновению». Причина: решение о внешнем виде
принимается, когда варианты сопоставимы визуально и лежат рядом, а не когда
один вариант уже стоит на экране и его не с чем сравнить.

*Примечание при синхронизации сред: в CLI-сессии, в которой писался этот
протокол, инструмент `/design` не был виден как установленный скил — само
правило (канва → сравнение → вёрстка) при этом остаётся в силе независимо
от того, в каком инструменте выполняется правка.*

## 10. Проверочные ворота (что реально гоняется)

Перед тем как считать изменение готовым:

```bash
npm run lint   # eslint
npm test       # vitest: чистые функции, крипто, серверная комната
npm run e2e    # playwright: контраст (AA), зоны касания 44px, вёрстка на 375px
```

`e2e/contrast.spec.ts` и `e2e/touch.spec.ts` — не просто тесты, а часть этого
протокола в исполняемом виде: любое изменение цвета или интерактивного
элемента, нарушающее §1.2 или §5.1, должно упасть здесь раньше, чем дойдёт
до пользователя. Скриншотных сравнений в проекте намеренно нет — они падают
от смены шрифта и не объясняют, что именно сломалось; вместо них —
точечные проверки конкретных инвариантов (контраст, размер хит-зоны,
отсутствие горизонтального переполнения на узком экране).

Новый инвариант дизайн-системы (новое обязательное значение контраста,
новый минимальный размер, новое правило раскладки) по возможности оформляется
такой же проверкой, а не только строкой в этом документе — иначе он держится
на памяти, а не на CI.

## 11. Чек-лист перед правкой

1. Цвет — беру существующий токен текста/заливки (§1); новый — только с
   измеренным контрастом на всех своих фонах.
2. Кегль — существующая ступень целиком (размер+интерлиньяж+трекинг), не
   произвольное значение (§2).
3. Отступ/радиус/тень — существующий токен, шаг 4px (§3).
4. Иконка — существующая ступень размера и веса; новый глиф — по правилам
   §4.2, если он в зоне «часто видимого».
5. Интерактивный элемент — зона касания ≥44×44, при необходимости через
   `HIT_SLOP_44` (§5.1).
6. Анимация — спокойный ритм, не пружина без причины; учтена в глобальном
   `prefers-reduced-motion` (§6).
7. Текст пользователю — на языке пользы, не реализации; если это видимое
   изменение — строка в `changelog.ts` тем же коммитом (§7.1).
8. Если функция скрывает/защищает данные — интерфейс не выдаёт сам факт
   скрытия и не обещает больше, чем делает код (§7.2).
9. Экран/иконка — сначала канва в `design/`, потом вёрстка (§9).
10. `npm run lint && npm test && npm run e2e` — зелёные (§10).
